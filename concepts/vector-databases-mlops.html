Vector Databases & MLOps

A great model is only the beginning. Getting it to run reliably, be searchable, and stay accurate in production requires an entire supporting infrastructure layer.

01 The plain-English version

A vector database stores embeddings and is built to answer one question extremely fast, even across billions of entries: "which stored items are most similar to this new one?" — the core operation behind semantic search and RAG systems.

MLOps is the discipline of reliably building, deploying, monitoring, and updating machine learning models in production — the ML equivalent of DevOps, dealing with problems unique to models, like performance quietly degrading as the real world drifts away from the training data.

02 The formal version

Vector databases (like Pinecone, Weaviate, or pgvector) use Approximate Nearest Neighbor (ANN) search algorithms — such as HNSW (Hierarchical Navigable Small World graphs) — to find close matches in high-dimensional embedding space in roughly logarithmic time, trading a small amount of accuracy for massive speed gains over brute-force comparison against every stored vector.

MLOps pipelines typically include: automated retraining triggers, A/B testing of new model versions against production traffic, and monitoring for data drift (when incoming data's statistical properties diverge from training data) and model drift (when real-world performance degrades over time even without input changes) — since a model that was accurate at launch can silently become unreliable as the world it's making predictions about changes.

03 The flow

Production ML is a loop, not a one-time deployment — models need continuous monitoring and periodic retraining to stay accurate as real-world data shifts.

04 Worked example

Data drift in practice

A fraud-detection model trained on 2023 transaction patterns might see its precision quietly drop from 91% to 78% over a year — not because the model changed, but because fraud tactics evolved and no longer match the patterns it learned. An MLOps monitoring system tracking live precision against a labeled sample would catch this decline and trigger a retraining pipeline, rather than the degradation going unnoticed until it causes real business harm.

05 Where this shows up

Real-world use

Vector databases are the retrieval backbone of nearly every production RAG system and semantic-search product. MLOps practices are what separate a model that works well in a research notebook from one that reliably serves millions of real users — the gap between the two is a large part of why so many promising ML projects never make it to sustained production use.

06 Common misconceptions

✕

Once a model is deployed, the work is done. Production models require ongoing monitoring — the world the model makes predictions about keeps changing, and the model doesn't automatically know that.

✕

Vector search always returns the mathematically closest matches. Approximate nearest neighbor methods deliberately trade a small amount of accuracy for large speed gains — "approximate" is in the name for a reason, and it's a reasonable trade-off at scale.

✓

Correct framing: the majority of the engineering effort in a real AI product often goes into this operational layer — deployment, monitoring, retrieval infrastructure — not into training the model itself.
