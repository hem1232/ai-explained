RAG & AI Agents

A language model's knowledge is frozen at training time and limited to what was in its training data. RAG and agents are the two dominant ways of working around that limitation.

01 The plain-English version

RAG (Retrieval-Augmented Generation) gives a model access to outside information at the moment you ask a question: it searches a document collection for relevant passages, then hands those passages to the model along with your question, so it can answer using current or private information it was never trained on.

An AI agent goes a step further — instead of answering in one shot, it can plan a sequence of steps, use tools (search the web, run code, query a database), observe the results, and decide what to do next, looping until the task is actually done.

02 The formal version

RAG systems convert documents into embeddings and store them in a vector database. At query time, the user's question is also embedded, and the system retrieves the nearest-neighbor document chunks by vector similarity, injecting them into the model's context window alongside the original question — grounding the model's answer in retrieved text rather than relying purely on parametric memory from training.

Agent frameworks typically implement a loop — often described as ReAct (Reason + Act): the model generates a thought, chooses an action (like calling a specific tool with specific arguments), receives an observation (the tool's output), and repeats, incorporating each observation into its next reasoning step, until it determines the task is complete or a stopping condition is hit.

03 The flow

RAG's core loop: turn the question into a search, find relevant real documents, and generate an answer grounded in them — rather than relying solely on what the model memorized during training.

04 Worked example

An agent chaining tool calls

Task: "What's the weather in the city where our biggest customer is headquartered?" An agent might reason: (1) I need to find the biggest customer → calls a database-query tool → gets "Acme Corp, headquartered in Austin." (2) Now I need Austin's weather → calls a weather-API tool → gets "78°F, clear." (3) I have enough information → responds to the user with the final answer. No single tool could answer this alone; the agent had to chain two tool calls together based on the result of the first.

05 Where this shows up

Real-world use

RAG is behind most "chat with your documents" products and enterprise AI assistants that need to cite internal company data, since it lets an off-the-shelf model answer accurately about information it never saw during training. Agents power coding assistants that can run and test code, research assistants that browse the web, and increasingly, multi-step business-process automation.

06 Common misconceptions

✕

RAG updates the model's actual knowledge, like fine-tuning would. RAG doesn't change the model's weights at all — it just supplies extra text as context at query time; the underlying model is unchanged.

✕

Agents can reliably handle any multi-step task without supervision. Agents can compound errors across steps, and a wrong tool call or misread observation early in a chain can derail everything that follows — reliable agent systems need careful guardrails, not just a capable underlying model.

✓

Correct framing: RAG solves "the model doesn't know this fact"; agents solve "this task needs more than one step and real-world actions" — related but different problems, often combined in the same system.
